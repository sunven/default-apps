**多个文件类型统一设置默认应用 · 设计方案**

状态：用户已确认完整方案；实现、自动测试、受控桌面验收和正式打包已完成。真实系统的批次完成回调本轮尚未观察到，具体证据与限制见[验收记录](batch-file-associations-validation.md)。本文件是 [spec.md](../spec.md) 的批量设置增补规格。

最终主流程：**勾选多个文件类型 → 选择同一个应用副本 → 预览实际变更 → 一次确认后逐项执行 → 查看每项结果**。支持停止后续设置，并保存最近一批供重开后确认继续；中途更换目标应用时，只将待处理项带入一个新批次。

**已明确的需求**

- 用户目标：让自己日常管理默认应用更省事。
- 用户原话：“做勾选批量设置，可以一次为多个文件类型，选择用一个应用打开。”
- 结合本轮功能选择，批量设置指为多个文件类型统一选择同一个默认应用；这次请求覆盖文件类型。
- Q1 已确认：文件类型页先勾选多项，再统一选择一个应用，预览后开始设置。
- Q2 已确认：一次确认清单后由工具逐项执行，允许部分成功并保留成功项；系统可能逐项确认。
- [领域词汇表](../GLOSSARY.md)已加入“批量设置”，区分选择过程与系统已完成修改。

**已核对的当前事实**

- 当前修改服务每次受理一个关联和一个具体应用副本；有结果未定的请求时阻止新写入。
- 每次提交会检查最新默认是否仍符合用户看到的值，并重新检查目标副本可用性。
- 当前成功条件是系统完成成功且回读匹配目标副本路径；受理成功不等于修改成功。
- 当前保存单条未定记录；退出不会撤回系统请求，重开不会自动重放旧请求。
- 现有界面提供应用、文件类型和协议三个入口；批量选择、批量执行和批量结果视图需要新增设计。
- 当前目标应用无需属于系统候选，也无需声明支持所选类型；现有流程允许手动选择具体应用副本。系统候选与支持声明均不保证最终设置或打开成功。
- 当前服务在系统完成后取得可信回读才结束请求；明确失败也可能结束请求，但尚无系统完成或回读失败时仍阻止后续写入。这是当前服务约束，不表述为 macOS 禁止批量操作。

这些事实限制方案如何实现，但没有替用户决定多选入口、失败后的行为或重开后的使用体验。

**已确认的交互方案**

以下布局已随完整方案获得用户确认。

1. 文件类型列表增加独立复选框。点击名称仍查看详情；复选框表示批量选择，不能与当前浏览焦点混为一谈。未解析项目显示原因并不可勾选。选择集合按具体文件类型身份去重，同扩展名的不同类型仍分开呈现。
2. 有勾选时显示操作条：“已选 N 个类型”“查看已选”“清空”“选择应用…”。全选表示当前搜索／筛选后的全部可识别结果，不仅是屏幕可见行；取消当前结果的全选只影响这些结果，保留其他搜索下已选项。
3. “选择应用”面板提供搜索，合并已发现应用与系统返回的候选副本，优先展示全部已选类型的共同候选；显示名称、版本、路径及候选覆盖情况，保留“选择其他应用…”。候选查询失败时标记覆盖未知，不把失败当成零覆盖或不支持。
4. 选好应用进入预览，逐项显示名称、扩展名、类型身份、当前默认和共同目标。只读准备期间不产生系统修改；可以返回调整选择和应用。显示实际拟修改项数；没有可执行项时只展示原因，不能开始空批次。
5. 点击“开始设置 N 项”后固定本批清单及顺序。全局状态条展示总进度、当前类型、目标应用、详情和“停止后续设置”；等待时明确是哪一项未定，仍能浏览其他入口。
6. 批次详情按项目展示结果，并汇总已确认修改、已是目标、明确失败、需重新确认、不执行的原因、未执行和结果未定。只有全部拟修改项已得到确定处理结果，才表示本轮处理结束；“处理结束”与“全部设置成功”分别呈现。
7. 停止或结束后保留最近一批结果。继续尚未提交项、重新处理问题项都先重新查询和预览；浏览器式前端重载只重取进度，不能再发起整批。
8. 继续或重试时若共同目标仍是原副本，沿用当前批次并保留各项结果；若明确换成另一个副本，将待处理项带入新批次重新预览。新批次开始时才替换旧批记录，取消预览不会丢掉旧批次。

已开始批次与尚未开始的勾选分开：前者由后端持有并保存，后者只在本次打开期间保留。开始后清空用于这次提交的勾选；正在执行时统一禁用新的勾选提交与其他修改入口。切换浏览入口不影响批次执行，也不改变已固定的清单。

**场景与结果规则**

| 场景 | 项目结果／下一步 | 对后续项的影响 |
| --- | --- | --- |
| 已是同一目标副本 | 显示“已是目标”，无需发起修改 | 继续 |
| 预览时无法解析／无法获得可信当前默认 | 列出不执行的原因；可在问题处理后重新预览 | 其他可执行项正常开始 |
| 执行前默认与已确认预览不同 | 本次不写入，标记“需重新确认” | 继续其他项 |
| 执行前检查失败且确定尚未受理请求 | 列明检查失败、本次未提交；可手动重新处理 | 继续其他项；目标失效或存储故障按整批问题处理 |
| 系统完成成功且回读为目标规范路径 | “已确认修改” | 进度保存成功后继续 |
| 系统已返回错误且回读可信，或完成后可信回读不匹配目标 | 显示明确的失败／不匹配结果与实际观察 | 进度保存成功后继续 |
| 提交应答丢失 | 核对原尝试身份和受理状态；不能换新请求重发 | 等待核对明确 |
| 无系统完成，或完成后回读失败 | “结果未定”；可以重新查询，但不能把查询到目标当成旧请求已结束 | 等待；没有超时自动判失败或跳到下一项 |
| 用户停止后续设置 | 锁住下一项推进；正在受理／已提交项继续处理实际结果 | 余下保持未执行，不自动继续 |
| 目标副本失效或批次／请求进度保存失败 | 暂停并展示问题；只能声称已知的内存状态与已持久事实 | 处理后重新预览确认 |
| 退出或进程终止后重开 | 展示最近批次；未定项与真正未提交项分开恢复 | 不自动继续、重试或重放 |

上述自动推进以“用户没有停止、没有退出、没有整批故障、进度已可靠保存”为共同前提。查询到当前默认发生变化只说明观察到差异，不能推断是哪个外部应用修改的。

例如选择 Markdown、纯文本、JSON、RTF 四项统一使用应用 A：Markdown 成功、纯文本原本已是 A、JSON 提交前被外部改成 B、RTF 系统明确拒绝且回读可信，则结果为“已确认修改 1、已是目标 1、需重新确认 1、失败 1”，不显示“4 项设置成功”。重新处理 JSON／RTF 必须再次预览；Markdown 不因这次重试再次执行。

**实现所需的一致性约束**

这些约束来自已确认行为及现有代码的实际边界，属于实现方案，保持在规格中，不写入领域词汇表。

- Go 持有已开始批次、执行推进、停止状态、全局写入归属和恢复；前端发送用户命令并呈现带版本的快照。单项仍经过现有受理、系统完成和回读验证路径。
- 批次互斥覆盖两项之间的空隙及所有单项入口；只禁用界面按钮或只检查单项 Busy 不足以满足 Q9。停止、退出与下一项受理必须有明确先后边界。
- 批次身份与单次修改尝试身份分开。重复点击开始、前端重载、重连及提交应答丢失不能产生额外原生写入；核对继续使用原尝试身份，用户明确重试才创建新尝试。
- setter 前将批次项与原请求身份、单条未定记录在同一次配置更新中关联。完成后将项目已知结果和对应未定记录的清除原子协调，避免请求证据消失而批次仍显示“尚未执行”。
- 保存失败时暂停后续推进；现有原子写在 rename 后的目录同步也可能失败，因此保存报错不能证明磁盘一定未改变。恢复依据实际持久事实，无法确定的受理窗口保守显示未知，不能借重开自动再发。
- 旧配置需要兼容读取和明确迁移；未知版本或损坏配置保留原文件并报告。保存手动关联、应用位置、未定请求和批次进度时保持其他字段，沿用同一配置存储的串行更新。
- 配置在首次保存批次时从版本 1 升到版本 2；读取兼容两者，单纯浏览不迁移。旧版程序严格拒绝版本 2，因此降级前需先处理配置兼容，不能预期旧版忽略批次字段。
- 重开时已保存的成功／失败表示当时的处理结果；当前默认需要重新查询，不能把旧结果直接描述为现在仍然生效。
- 退出与重启安装复用现有统一入口，同时处理整批尚有未执行项的情况；确认退出后先停止下一项推进，当前已提交请求的未知语义保持一致。
